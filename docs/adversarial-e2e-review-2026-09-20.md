# 서면 SaaS 적대적 E2E 검토

검토일: 2026-09-20  
범위: 개인 계정형 웹서비스, 문체 프로필, 사건 입력, 법률 근거, 초안 생성, 검증, 공식 판례 연동

## 결론

현재 제품은 계정 격리와 근거 패킷을 검증하기 위한 SaaS 기반으로는 동작한다. 그러나 생성 결과를 한국 민사소송의 제출 가능한 준비서면 초안으로 평가하면 출시 불가다. 현재 웹 경로에는 LLM과 버전 관리된 프롬프트가 없고, 문체 프로필 중 실제 출력에 영향을 주는 요소도 제한적이다. 형식 검사는 출처 ID 존재를 확인할 뿐 문장과 근거의 의미상 함의를 검증하지 않는다.

따라서 제품 표현은 다음처럼 분리한다.

- 현재 제공 가능: 개인 계정, 자료 저장, 승인 경계, 공식 판례 검색·가져오기, 근거 ID가 붙은 검토용 개요
- 아직 제공 불가: 잠재적 논증 체계의 신뢰도 높은 추출, 판례의 사건 적합성 판단, 제출 가능한 완성 서면, 의미상 무환각 보증

## 검토 역할과 토론 결과

### 법률 실무 관점

합성 대여금 사건을 사용한 E2E에서 다툼 있는 사실과 청구 취지가 사실관계와 동일하게 출력되고, 사건번호·법원·당사자·소송 단계·청구취지·입증책임·요건사실·상대방 주장별 답변이 없었다. 허위 법률 근거도 수동 승인만으로 초안에 들어갈 수 있었다.

최소한 다음 계약이 있어야 제출용 초안으로 평가할 수 있다.

1. 문서 유형과 절차 정보
2. 청구·항변별 요건사실과 입증책임
3. 상대방 주장별 인정·부인·부지 응답
4. 사실별 증거와 정확한 쪽/문단 위치
5. 법률 명제별 공식 판례·법령 원문과 핀포인트
6. 반대 논거와 미확인 사항
7. 변호사 최종 승인 및 수정 이력

### 프롬프트 엔지니어링 관점

현재 웹 생성은 문자열 템플릿이며 실제 프롬프트 파이프라인이 아니다. 기존 서면 분석은 문장 길이, 제목, 서증 표지, 결론 선제시 여부 정도만 추출한다. 이를 “무의식적 사고 체계”라고 부르면 구현보다 강한 주장이다.

또한 기존 서면, 사건 기록, 법률 명제는 모두 비신뢰 데이터다. 모델을 연결할 때 자료 안의 `SYSTEM`, `ignore previous instructions` 같은 문구가 지시로 승격되지 않도록 시스템 지시와 소스 패킷을 분리해야 한다.

권장 모델 단계는 네 개다.

1. `profile_extractor_v1`: 여러 문서에 반복된 관찰 가능한 작성 행동만 구조화
2. `argument_planner_v1`: 주장·요건·입증책임·사실·증거·법률 근거의 문단 계획 생성
3. `legal_drafter_v1`: 승인된 계획만 문장화
4. `grounding_verifier_v1`: 별도 모델과 결정론 검사로 원자 주장별 함의 판정

### 시스템 엔지니어링 관점

문체 분석에서 평균을 문장마다 재계산해 입력 크기가 두 배가 될 때 시간이 약 네 배 증가하는 문제가 확인됐다. 이 부분은 평균을 한 번만 계산하도록 수정했고, 분석 작업을 요청 이벤트 루프 밖에서 실행하며 입력 총량 상한을 추가했다.

SQLite와 전체 JSON 객체 저장은 파일럿에는 충분하지만 다음 단계에서는 PostgreSQL, 암호화 객체 저장소, 분산 rate limit/cache, 작업 큐가 필요하다. 프로필 분석·판례 조회·모델 생성은 동기 HTTP 요청이 아니라 멱등 작업으로 옮기고, 패킷과 초안 저장은 하나의 트랜잭션 또는 재개 가능한 상태 머신으로 묶어야 한다.

### 보안·개인정보 관점

계정 ID를 요청자가 넘기지 않고 세션에서 결정하는 점, CSRF·Origin·Host 검증, 세션 폐기, SQLite 파일 권한은 적절하다. 반면 실제 법률 자료는 평문이며 삭제·보존·감사 이벤트가 없다. 수동 URL은 승인됐다는 이유만으로 공식 검증된 근거처럼 취급하면 안 된다.

공식 판례 커넥터는 고정된 법제처 호스트만 호출하고, API 인증값을 브라우저로 보내지 않는다. 가져온 판례에는 공식 ID, 조회 시각, 내용 해시, 공개 원문 링크를 저장한다. 그래도 변호사의 개별 승인은 별도로 필요하다.

### QA 관점

브라우저 E2E에서 로그인, 로그아웃, 재로그인 후 영속성, 계정 간 격리, CSRF, Host/Origin 차단, 요청 크기 제한, XSS 이스케이프는 통과했다. 다음 실패가 재현됐다.

- 문자열 `"false"`가 관점 승인으로 해석됨
- UI의 “선택한 근거” 문구와 달리 모든 근거가 일괄 승인됨
- 승인된 모든 문체 trait를 실제 적용한 것처럼 보고함
- 날짜와 번호 제목이 문장으로 분리되어 문체 통계를 왜곡함
- `제544조은(는)` 같은 템플릿 문법 오류
- 허위 판례가 형식 검사에 통과함

이번 변경에서 엄격한 boolean 검증, 개별 체크박스 승인, 실제 적용 trait만 보고, 날짜/제목 문장 분리 보정, 문법 템플릿 수정, “기계 검사”를 “형식 검사”로 축소했다.

## 공식 한국 판례 데이터 결정

1차 제공자는 법제처 국가법령정보 공동활용 API다.

- 판례 검색: `lawSearch.do`, `target=prec`
- 판례 본문: `lawService.do`, `target=prec`
- 운영 인증: 등록한 `OC`를 서버에서만 보관
- 저장 provenance: 공식 판례 ID, 원문 링크, 조회 시각, 내용 SHA-256
- 제한: 주요 공개 판례 중심이며 전체 법원 기록을 보장하지 않음

대법원 종합법률정보의 화면용 내부 요청을 스크래핑하지 않는다. 현재 공개된 SaaS용 전체 판례 검색 API가 확인되지 않았고, 공식적으로 단계적 공공데이터 확대가 진행 중이다. 헌법재판은 공공데이터포털의 헌법재판소 REST API를 후속 어댑터로 추가할 수 있다.

## 출시 게이트

다음 조건 전에는 실제 의뢰인 자료를 받는 유료 법률 작성 서비스로 출시하지 않는다.

- 공식 OC와 이용량 협의
- 저장·백업 암호화, 삭제·보존 정책, 감사 이벤트
- 문서 유형별 절차 필드와 claim/defense matrix
- 네 단계 프롬프트 및 모델 버전 고정
- 원자 주장 100% source mapping
- 허위 사실·법령·판례·인용문 0건인 적대 평가 세트
- 실제 변호사 3~5명의 블라인드 검토와 편집시간/채택률 측정
- 공급자의 학습·보존 제외 계약과 한국 리전/전송 정책 확인

## 후속 구현 및 재검증

초기 적대 검토에서 지적한 구조적 결함에 대해 다음 통제 장치를 추가했다.

- 법원·사건번호·문서유형·작성 당사자·상대방·청구취지 입력
- 청구·항변별 요건, 입증책임자, 판단, 사실 ID, 법률 ID 매핑
- 상대방 주장별 인정·부인·부지·일부 인정 및 구체적 답변
- 법리의 적용 범위를 특정 요건 판단으로 한정하는 논증 단위
- 미승인 또는 누락 근거가 있으면 승인할 수 없는 논증계획
- 국가법령정보센터의 판례뿐 아니라 현행 법령 조문 검색·고정
- 문장과 인용 근거 사이의 어휘 연관성이 전혀 없을 때 차단하는 검사
- 문체의 지배적 전환어, 문장 길이, 종결어미, 결론 선제시, 서증 배치 규칙

재검증은 한 계정에 합성 서면 100개를 HTTP로 저장한 다음 프로필 생성,
사건 기록·법률 근거·관점 승인, 요건/입증책임/상대방 답변 입력,
논증계획 생성·승인, 구조화 초안 생성까지 한 흐름으로 수행했다. 90개 문서의
지배 문체와 10개 이례 문체를 섞은 별도 검사에서도 지배적 전환어를 유지했다.

이 변경으로 초기 보고서의 “claim/defense matrix 없음”과 “제출 정보 없음”은
해소됐다. 다만 다음 한계는 유지된다.

- 요건사실·입증책임·포섭 결론은 모델이 법적으로 추론하는 값이 아니라 변호사가
  입력하고 승인한 구조다.
- 공식 검색 결과가 해당 사건에 가장 적합한 판례인지 자동 판정하지 않는다.
- 의미 일치 검사는 어휘 기반 가드레일이지 자연어 함의 검증기가 아니다.
- 서명·첨부목록·전자소송별 세부 양식과 HWP/DOCX 출력은 구현되지 않았다.
- 실제 변호사 블라인드 평가와 실제 의뢰인 자료 검증은 아직 수행하지 않았다.
